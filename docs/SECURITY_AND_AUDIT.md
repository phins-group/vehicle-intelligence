# Security and Audit

## Scope

The platform authenticates HTTP clients with either high-entropy API keys or
OIDC/JWKS bearer JWTs, authorizes each route through explicit RBAC permissions, and
appends actor-oriented audit records for successful security-sensitive actions.
The application layer depends on an `Authenticator` port, so route permission
policy does not depend on the selected identity provider.

This is API authentication, not camera authentication. RTSP credentials remain
under the separate encrypted camera-credential boundary.

## Authentication

Authentication is intentionally disabled in the default local-development
configuration. When disabled, protected routes execute as the visible synthetic
principal `development-admin` with authentication method `DEVELOPMENT`; system
health reports `authentication: disabled`.

Production must enable authentication and configure at least one active `ADMIN`.
Startup validation fails closed if no active administrator exists, IDs/hashes are
duplicated, or a verifier is malformed.

Generate a key/verifier pair:

```bash
python scripts/generate_api_key.py
```

The raw key is displayed once and belongs in a password/secret manager. Only its
lower-case SHA-256 verifier belongs in configuration:

```bash
export VIP_AUTH__ENABLED=true
export VIP_AUTH__PRINCIPALS='[
  {
    "id": "admin-01",
    "display_name": "Platform Admin",
    "role": "ADMIN",
    "key_sha256": "<64-hex-verifier>",
    "enabled": true
  }
]'
```

Pydantic accepts JSON aliases/field names in environment values according to the
settings parser. The raw key is sent as:

```http
Authorization: Bearer <raw-high-entropy-key>
```

The server hashes the presented value and performs constant-time comparisons
against active verifiers. Missing/invalid credentials return `401` with a generic
message; authorization failures return `403`. Neither response contains the
credential. `/api/system/health`, `/livez`, and `/readyz` remain public and expose
only bounded capability/dependency states; `/api/auth/me` returns the authenticated
principal.

Bearer keys provide no confidentiality on the wire. TLS termination is mandatory
outside isolated local development. Keys should have at least the entropy
generated by the supplied script. Rotation currently requires adding a second
principal/key, updating clients, then removing the old entry.

For centralized identity, set `VIP_AUTH__PROVIDER=oidc` and configure an exact
issuer, JWKS URL, one or more audiences, an explicit `RS256`/`ES256` allowlist,
and role mapping. JWT-provided `alg` values never expand that allowlist. Signature,
issuer, audience, expiry, subject, and bounded role/name claims are verified;
JWKS resolution is cached and fails closed. HTTPS is mandatory unless an explicit
local-development override is configured. This follows [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0-18.html)
and the [JWT Best Current Practices algorithm guidance](https://www.ietf.org/rfc/rfc8725.html).

The operator console obtains only public OAuth metadata from `/api/auth/config`.
It uses Authorization Code + PKCE S256, validates a one-use state transaction,
and stores the access token in memory rather than browser storage. Configure
`auth.oidc.console` with exact HTTPS authorization/token/logout endpoints, the
public client ID, scopes, and `/login` callback. The IdP remains responsible for
user lifecycle, MFA, access-token lifetime, revocation, and token-endpoint CORS.

SSE uses the normal Bearer header. Browser WebSocket clients authenticate in the
first TLS-protected frame because browser APIs cannot set an arbitrary handshake
header. Raw keys are deliberately rejected in realtime URL query parameters.
Unauthenticated WebSockets have a short bounded authentication deadline; ingress
connection/rate limits are still required in production.

## RBAC matrix

| Capability | VIEWER | OPERATOR | ADMIN |
|---|:---:|:---:|:---:|
| Read events, signed event media, realtime streams, live preview, vehicles, cameras, health, watchlists, rules, alerts | Yes | Yes | Yes |
| Test camera connection or run credential-free ONVIF discovery | No | Yes | Yes |
| Acknowledge/resolve alerts | No | Yes | Yes |
| Review OCR plates and read dataset-feedback queue | No | Yes | Yes |
| Create/update/delete cameras, including bounded batch creation | No | No | Yes |
| Create/update/delete watchlists and rules | No | No | Yes |
| Read audit logs | No | No | Yes |

Whitelist/rule changes remain administrator-only because they can ultimately
authorize physical barrier actions. Alert actors come from the authenticated
principal. The deprecated optional `actorId` body field is only a consistency
check and returns `403` if it differs from the principal; clients should omit it.

## Signed media capability

`GET /api/events/{eventId}/media` requires `READ_PLATFORM`. The caller cannot
submit an object key: FastAPI loads the authorized event and signs only its
persisted, relative media references after checking object existence. The API
response is private/no-store and the configured lifetime is bounded from 30
seconds to one hour.

A presigned URL is a temporary bearer capability. Anyone who receives it can
read that one object until expiry, independently of later API-key revocation.
Production therefore requires TLS, a short TTL, referrer-safe links, protected
application logs, and a browser-reachable `VIP_MINIO__PUBLIC_ENDPOINT`. The
secret access key is never serialized; the S3 credential identifier and
signature are expected query fields. The Angular UI does not write signed URLs
to browser storage and refreshes them only while the event drawer is mounted.

The bundled Nginx deployment sets the public endpoint to its own origin and
proxies only the signed `/vehicle-media/` bucket path to internal MinIO while
preserving the browser Host required by SigV4. Access logging is disabled for
that location so signed query strings do not enter gateway logs. CSP remains
`img-src 'self' data:` and `media-src 'self'`; it is not relaxed to arbitrary
HTTP(S) origins.

MinIO remains private. There is no public bucket policy, arbitrary-key signing
route, directory listing, upload route, or browser exposure of storage
credentials. Media reads are not mutation audits; ingress/object-store access
logs should provide read telemetry without recording full signed query strings.

## Audit lifecycle

Successful mutations synchronously append one immutable `AuditLog`:

```json
{
  "_id": "aud_...",
  "schemaVersion": 1,
  "actor": {
    "id": "admin-01",
    "displayName": "Platform Admin",
    "role": "ADMIN",
    "authenticationMethod": "API_KEY"
  },
  "action": "CAMERA_UPDATED",
  "resource": {"type": "CAMERA", "id": "gate-01"},
  "requestId": "req_...",
  "before": {},
  "after": {},
  "metadata": {},
  "occurredAt": "2026-08-09T12:00:00Z"
}
```

Audited actions:

- camera create (single or batch), update, delete, enable, disable, connection
  test, and ONVIF discovery result count;
- watchlist create, update, and delete;
- rule create, update, and delete;
- alert acknowledge and resolve.
- plate correction or confirmation, including before/after prediction, final
  value, review revision, and deterministic dataset-sample ID when present.
- detector-label review and immutable detector-dataset promotion.

`X-Request-ID` is accepted when it contains only safe identifier characters and
is at most 128 characters. Otherwise the API generates a new ID. Every response
echoes the effective ID, and every audit record keeps it.

Audit snapshots recursively redact credential-like keys, Bearer values, RTSP
URIs, URL user-info, and HTTP URL query/fragment values. Collection size, depth,
and string length are bounded. Camera snapshots originate from the public schema,
so plaintext/encrypted RTSP values never enter the audit service. Rule action
bodies must not contain secrets. External-action credentials now come only from
server configuration: a target can use managed Bearer authentication or an
HMAC-SHA256 signature over timestamp, idempotency key, method, request target,
and body hash. Target HTTPS policy, exact hostname, redirects, URL credentials,
fragments, length, method, timeout, and response retries are enforced centrally.
A per-target CLOSED/OPEN/HALF_OPEN breaker suppresses repeated infrastructure
failures; an open-circuit rejection does not consume the durable action retry
budget.

## Audit API

Only `ADMIN` can query audit records:

```http
GET /api/audit-logs?actorId=admin-01
GET /api/audit-logs?action=CAMERA_UPDATED
GET /api/audit-logs?resourceType=CAMERA&resourceId=gate-01
GET /api/audit-logs?from=...&to=...&limit=50&cursor=...
GET /api/audit-logs/{id}
```

Listing is newest-first with an opaque cursor. There is deliberately no update or
delete API. MongoDB has actor/time, resource/time, action/time, and cursor indexes;
no TTL is applied.

## Failure semantics and limitations

Audit writes are synchronous and required. The production Compose topology runs
MongoDB as a replica set and enables a request-scoped transaction around every
audited resource mutation. Repositories share one `AsyncMongoClient`; PyMongo's
bound session automatically applies to resource, dataset-feedback, and audit
writes. An audit failure aborts the complete transaction. Startup fails closed
if transactions are enabled against standalone MongoDB. This matches the
[PyMongo transaction model](https://www.mongodb.com/docs/languages/python/pymongo-driver/current/crud/transactions/).

Human review spans an event amendment, optional deterministic dataset-sample
upsert, and audit append in the same transaction when production transactions are
enabled. Development may deliberately keep transactions disabled; that mode is
not the strict production audit profile.

Detector-label review is filesystem-backed, so it uses a transactional outbox
instead of pretending a filesystem/Mongo transaction exists. The immutable
decision revision contains the sanitized `AuditLog` intent in the same exclusive,
fsynced JSON write. The API then delivers it to the audit repository and returns
`X-Audit-Delivery: delivered`; an audit outage returns a successful committed
review with `pending`. A bounded background relay retries pending intents, and a
checksum-bound delivery marker records completion without rewriting review
history. Audit append retries are idempotent by audit ID, covering a crash after
append but before marker creation. Promotion remains prepare-audit-dispatch: if
its mandatory pre-dispatch audit fails, the queued job is marked failed and is
never started.

The current milestone does not provide:

- password login, user CRUD, token issuance, refresh tokens, or per-session
  revocation (these remain the external identity provider's responsibility);
- API-key expiry or online rotation under one unchanged principal ID;
- account lockout, ingress TLS, WAF, or IP policy; the bundled web gateway applies
  bounded per-client API and WebSocket limits, but the public ingress must enforce
  the site-wide policy and trusted-client-IP boundary;
- persisted audit records for failed authentication/authorization attempts;
- immediate revocation of already issued presigned media URLs or per-object read
  audit records in MongoDB;
- cryptographic audit-chain signing or external immutable/WORM export.

Ingress/access logs should capture denied attempts without logging the
`Authorization` header.

## Camera credential key rotation

`SecurityConfig` accepts a retained decrypt keyring and exactly one active key.
New/updated camera secrets always use the active key ID while old `v1` tokens
remain decryptable. Rotate online with a dry run first:

```bash
vehicle-credential-rotation --dry-run
vehicle-credential-rotation
```

The worker decrypts only in memory, re-encrypts with a fresh nonce, and performs a
compare-and-set against the old ciphertext. It does not increment camera
revision, reveal credentials, or restart workers. The aggregate result is
audited; old decrypt keys may be removed only after all documents report current.
